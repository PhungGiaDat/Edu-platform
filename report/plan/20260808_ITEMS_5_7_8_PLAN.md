## #7 — Unity Editor Server Split + MCP Protocol Sanitize (Unity deferred)

### Goal

The Unity integration currently combines:
- An editor-only HTTP/TCP server (used by the `unityMCP` namespace tools for live editor control)
- The MCP protocol layer that exposes those tools to Cursor

These two concerns are tangled in the Unity codebase, with mixed auth, mixed logging, and shared command dispatch.

You asked me to **plan the non-Unity parts** and **defer the Unity implementation**. The non-Unity scope is:

### 7.1 — Audit current Unity MCP protocol surface

**File:** `plan/UNITY_MCP_AUDIT.md` (new — written by a Unity-aware agent later)

**Audit topics:**
- List all exposed MCP tools (commands callable from Cursor → Unity)
- For each: identify auth requirement, log level, command-mutation class (read/write/destructive), rate-limit
- Identify the protocol transport (stdio, TCP, HTTP, named pipe)
- Identify whether commands are sandboxed (sandbox = "only operate on the test scene, not on user assets")

**Estimated effort:** 2–3 hours (requires running Unity editor and inspecting actual behavior). **Out of scope this session.**

### 7.2 — Define the contract between the editor server and the MCP protocol

**File:** `docs/architecture/UNITY_MCP_CONTRACT.md` (new)

**Contract shape:**
```
Editor Server (in-Unity):
  - Owns: AssetDatabase, SceneManager, BuildPipeline, ProBuilder
  - Exposes: a typed command interface (struct or interface)
  - Auth: requires editor-side authentication token
  - Logging: logs to Unity console + file

MCP Protocol Layer (Cursor-side):
  - Owns: protocol translation, rate limiting, tool registration
  - Does NOT own: Unity APIs directly
  - Sanitizes: input (length, type, path traversal), output (truncate, redact)
  - Auth: requires user-side authentication token
```

**The split:** Editor server exposes a typed API; MCP layer translates Cursor-side JSON to typed API calls. Neither can do the other's job.

**Estimated effort:** 1.5 hours of contract design. **Does not require Unity** — can be done as design only.

### 7.3 — Document the MCP input sanitization rules

**File:** `docs/architecture/MCP_SANITIZATION.md` (new)

**Rules (initial draft, to be refined):**
- All string inputs: max length 4096 chars
- All path inputs: must resolve under `Assets/`; reject `..`, absolute paths, symlinks outside Assets
- All numeric inputs: bounded to expected ranges per command
- All array inputs: max length 100
- All enum inputs: validated against allowed values
- All binary inputs: rejected (no base64 blobs through MCP)
- All output: truncation at 16 KB per response; redaction of absolute paths in returned strings

**Estimated effort:** 1 hour. Documentation only. **No Unity work.**

### 7.4 — Identify the breaking-change risk

**The split will require renaming or repathing MCP tools.** Any tooling that calls `unityMCP.foo_bar` will need updating. The plan must enumerate all such callers.

**Audit command:**
```bash
rg "unityMCP\." --type ts --type py --type md | head -50
```

**Estimated effort:** 30 min audit, 30 min migration doc.

## #8 — Replace Hardcoded Assets with Catalog Manifest + arTag/Index

### Goal

Currently, AR assets (glb files, mind targets, image targets) are referenced by hardcoded URLs in:
- Mobile Unity scripts (ComboManager.cs and others)
- Backend Mongo documents (ar_objects.model_3d_url field)
- Frontend AR viewer (ar-viewer.html, ARContainerV2.tsx)

The audit identified this as risky: asset URLs change, content teams can't update without code deploys, and there's no single source of truth.

The proposal:
- **Catalog manifest:** A single JSON document (hosted in Supabase, cached on clients) listing all AR assets by `arTag`.
- **`arTag` index:** A lookup table that maps `arTag` → `(catalog_id, target_index)`.
- **Backend Mongo:** Stores `mind_catalog_id` + `mind_target_index` (the catalog coordinates), not raw URLs.
- **Frontend/Unity:** Resolves URLs via the catalog manifest, not via hardcoded paths.

### Scope

**In scope this plan:**
- Data model design (backend Mongo schema changes)
- Catalog manifest JSON shape (file format, validation, hosting)
- Backend catalog service (the lookup API endpoint)
- Migration path from current hardcoded URLs to catalog references
- Frontend resolution logic (Unity deferred — only the *contract* with frontend)

**Out of scope:**
- Unity catalog client implementation (Unity work, deferred)
- Asset upload pipeline (separate feature)
- CDN caching layer (separate feature)

### 8.1 — Define the catalog manifest schema

**File:** `docs/architecture/CATALOG_MANIFEST.md` (new) + `backend/database/migrations/catalog_manifest_schema.json` (reference)

**Schema (draft):**
```json
{
  "version": 1,
  "catalogs": [
    {
      "id": "animals-v2",
      "name": "Animals (v2 catalog)",
      "targets": [
        {
          "index": 0,
          "ar_tag": "elephant_marker_01",
          "glb_url": "https://cdn.example.com/elephant.glb",
          "glb_size": 1234567,
          "animation_type": "idle",
          "position": [0, 0, 0],
          "rotation": [0, 0, 0],
          "scale": [1, 1, 1],
          "description": "Elephant idle animation",
          "thumbnail_url": "https://cdn.example.com/elephant-thumb.png"
        }
      ]
    }
  ]
}
```

**Validation rules:**
- `version` is an integer, starts at 1, monotonically increases
- `catalogs[].id` is unique within the manifest
- `targets[].index` is unique within a catalog
- `targets[].ar_tag` is unique across the entire manifest (global namespace)
- All URLs are HTTPS, point to whitelisted CDN domains

**Estimated effort:** 2 hours (schema design + validation script).

### 8.2 — Backend catalog service API

**New endpoint:** `GET /api/v1/catalog/manifest`

**Behavior:**
- Reads the catalog manifest from Supabase storage (`catalogs/manifest.json`)
- Returns the manifest as JSON
- Includes `Cache-Control: max-age=300` for client-side caching
- Includes ETag for conditional requests

**New endpoint:** `GET /api/v1/catalog/resolve/{ar_tag}`

**Behavior:**
- Looks up the `ar_tag` in the manifest
- Returns the catalog coordinates: `{catalog_id: "animals-v2", target_index: 0, glb_url: "..."}`
- 404 if the ar_tag is unknown

**File:** `backend/api/catalog_routes.py` (new)

**Estimated effort:** 3 hours (FastAPI routes + Supabase client integration + tests).

### 8.3 — Mongo schema migration

**Current:** `ar_objects` documents have `model_3d_url` (a hardcoded URL).

**Proposed:**
- Add `mind_catalog_id: str` (required for tracking_mode=catalog)
- Add `mind_target_index: int` (required for tracking_mode=catalog)
- Deprecate `model_3d_url` for catalog rows (still required for legacy rows per the contract)

**Migration:** The existing `repair_ar_objects_consistency.py` script already supports this transition via the consistency map. The map needs to be populated with the actual catalog coordinates from the new manifest.

**Estimated effort:** 2 hours (extend the consistency map, run dry-run, verify).

### 8.4 — Frontend resolution logic

**Current:** `frontend-web/src/pages/LearnARV2.tsx` and `frontend-web/public/ar-viewer.html` use hardcoded asset URLs.

**Proposed:**
- On page load, fetch `/api/v1/catalog/manifest`
- For each `ar_tag` in the lesson, look up coordinates via the manifest
- Use the resolved URL in the MindAR init code

**File changes (frontend, non-Unity):**
- `frontend-web/src/core/types/ARMessages.ts` — extend the type with `mind_catalog_id` and `mind_target_index`
- `frontend-web/src/core/catalog/catalogClient.ts` (new) — wraps the manifest fetch
- `frontend-web/src/components/ar/ARContainerV2.tsx` — uses catalogClient instead of hardcoded URLs

**Estimated effort:** 4 hours (frontend refactor). **Unity client deferred.**

### 8.5 — Backwards compatibility window

During the transition, both code paths must work:
- Legacy rows (`tracking_mode=legacy`) keep their `model_3d_url`
- Catalog rows (`tracking_mode=catalog`) resolve via the manifest

The contract in `apply_ar_objects_validator.py` already enforces this discriminator. So once the manifest is populated and the consistency map is repaired, the new behavior is automatic for catalog rows.

**Estimated effort:** 1 hour (testing the coexistence).

### Total #8 non-Unity effort: ~12 hours. Unity catalog client deferred.
