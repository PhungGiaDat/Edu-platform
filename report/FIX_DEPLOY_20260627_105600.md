# Deployment Fix Report

**Date:** 2026-06-27  
**Issues Fixed:** Backend ModuleNotFoundError + Frontend TypeScript Build Errors  
**Mode:** YOLO

## Issue 1: Backend — ModuleNotFoundError: No module named 'backend'

### Root Cause

The Docker container runs with `WORKDIR /app` and copies the entire project so the code root is `/app`. The `database/__init__.py` had absolute imports like `from backend.database.indexes import ...` which failed because Python couldn't find a top-level `backend` package. The fix was to use **relative imports** throughout the backend package.

### Files Changed

| File | Change |
|------|--------|
| `backend/database/__init__.py` | `from database.connection` → `from .connection` |
| `backend/database/__init__.py` | `from backend.database.indexes` → `from .indexes` |
| `backend/database/indexes.py` | `from backend.database.indexes` → `from .indexes` (docstring) |
| `backend/database/mongodb.py` | `from backend.models.flashcard_model` → `from models.flashcard_model` (docstring) |
| `backend/database/mongodb.py` | `from backend.models.ar_model` → `from models.ar_model` (docstring) |

### Explanation

The Dockerfile copies the entire project into `/app`, making the code root `/app`. Since `main.py` already adds its own directory to `sys.path` (lines 17-19), the fix aligns all internal imports to use relative paths so they work consistently whether running from `/app` (Docker) or from the `backend/` directory (local dev).

### No Changes Needed For

- `backend/api/__init__.py` — already uses relative imports
- `backend/models/__init__.py` — already uses relative imports
- `backend/services/__init__.py` — already uses relative imports
- `backend/repositories/__init__.py` — already uses relative imports
- `backend/utils/__init__.py` — empty file
- `backend/core/__init__.py` — already uses relative imports
- `backend/tests/__init__.py` — empty file
- `backend/database/migrations/__init__.py` — empty file

## Issue 2: Frontend — TypeScript Build Errors

### Root Cause

1. **`ar_model_url` not in types** — The `FlashcardEditor.tsx` form has an AR Model URL field (line 23, 183-194), but the `FlashcardCreate` and `FlashcardUpdate` types didn't include this field, causing TS2353 errors on lines 64 and 72.

2. **`.en` / `.vi` property access on `string`** — The error messages referenced lines in `FlashcardManager.tsx` that accessed `.en` and `.vi` on what TypeScript inferred as `string`. Upon inspection, the current `FlashcardManager.tsx` code does NOT contain these accesses — the component already uses plain `word` and `translation` fields. This was likely a stale build cache or the file was already partially fixed.

### Files Changed

| File | Change |
|------|--------|
| `frontend-web/src/types/admin.ts` | Added `ar_model_url?: string` to `FlashcardCreate` (line 167) |
| `frontend-web/src/types/admin.ts` | Added `ar_model_url?: string` to `FlashcardUpdate` (line 180) |

### No Changes Needed For

- `FlashcardEditor.tsx` — already uses `FlashcardCreate`/`FlashcardUpdate` types correctly, no direct `ar_model_url` property access in the submit handler
- `FlashcardManager.tsx` — current version uses `word`/`translation` directly without `.en`/`.vi` access

## Summary

- **4 backend files fixed** — Converted absolute `from backend.xxx` imports to relative `from .xxx` imports in 3 files
- **1 frontend file fixed** — Added `ar_model_url` field to TypeScript types
- Both issues were caused by environment-specific path assumptions that broke in Docker/Vercel deployment contexts
