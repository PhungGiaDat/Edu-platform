# Debug Report

## Issue Summary
**Description:** Production HTML requested `/assets/index-DryKqU7b.js`, and the browser received `404 Not Found`, leaving the Vite application unable to start.
**Severity:** High
**Status:** Fixed and verified locally

## Reproduction Steps
1. Request a nonexistent hashed path under `https://edu-platform-dun.vercel.app/assets/`.
2. Observe the `404 Not Found` response.
3. Observe that the same response receives `Cache-Control: public, max-age=31536000, immutable` from `frontend-web/vercel.json`.
4. A browser is therefore allowed to reuse the negative response without revalidation even after the asset becomes available.

## Evidence

### Error Messages/Stack Traces
```text
GET https://edu-platform-dun.vercel.app/assets/index-DryKqU7b.js
net::ERR_ABORTED 404 (Not Found)
```

During investigation, a fresh request to the same `index-DryKqU7b.js` URL returned `200 OK` with 891,336 bytes. A deliberately absent `/assets/index-NOTREAL.js` returned `404` while still receiving the one-year immutable cache policy. This explains why one browser could remain broken after production had recovered for fresh clients.

The live root document returned `Cache-Control: public, max-age=0, must-revalidate`, referenced `index-DryKqU7b.js`, and had no service-worker registration. The SPA rewrite excludes `/assets/`, so neither stale HTML policy, a service worker, nor the SPA fallback caused the asset response.

GitHub metadata for commit `3c5d13b` showed:

- Vercel's native Git deployment completed successfully.
- Both Actions-based Vercel jobs failed during `vercel pull`, before publishing.
- The repository nevertheless configured two additional production publishers, and one built with the preview environment before calling `vercel deploy --prod`.

The failed Actions jobs did not publish this incident's deployment, but leaving them configured would create a production-alias race if their credentials were restored.

## Root Cause Analysis

### The Problem
The repository applied a successful-asset caching policy to every `/assets/*` response regardless of status. A transient or version-skew 404 was therefore advertised to browsers as immutable for one year.

The deployment configuration also had multiple potential owners for the Vercel production alias: the active Vercel Git integration and two GitHub Actions paths. One Actions path incorrectly mixed a preview build with a production publish command.

### Why It Happens
Vite entry and lazy-chunk filenames are content hashed. A deploy or environment change produces a different filename. During version skew or a transient availability window, a client can request a hash that is not present in the deployment serving the asset request. The broad Vercel header rule then makes that negative response sticky in the browser.

## Implemented Fix
1. Kept Vercel's verified Git integration as the only production publisher.
2. Removed Actions production deploy commands while retaining CI and an optional pull-request preview.
3. Removed the one-year immutable browser policy that also matched negative `/assets/*` responses.
4. Registered Vite's `vite:preloadError` recovery with a 10-second cooldown and a history-state fallback when session storage is blocked.
5. Changed the entry bundle so affected browsers move from the previously cached URL to a new content hash after deployment.
6. Added deployment-policy and asset-recovery regression tests.
