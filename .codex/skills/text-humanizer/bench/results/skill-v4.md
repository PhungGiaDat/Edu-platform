## Task 2 — 02-blog-coffee-brewing.md

Great coffee isn't complicated, but it does come down to getting a few variables right: grind size, water temperature, brew time, and ratio. Start with 1:16 — one gram of coffee to sixteen grams of water — a solid baseline for most brewing methods. Temperature matters just as much: aim for 90–96°C. Go hotter and you pull out bitter compounds; go cooler and the cup tastes sour and underdeveloped.

Freshness is the variable people skip, and it shouldn't be. Beans start losing their aroma within two weeks of roasting, so buy whole beans in small batches and grind right before you brew.

None of this requires a trip to a café. Pour-over, French press, AeroPress, cold brew — whichever method you pick pulls something different out of the same beans. This guide walks through the fundamentals that turn an ordinary cup into something worth waking up for.

## Task 7 — 07-explainer-docker.md

# Understanding Docker Containers

A Docker container is a lightweight, standalone package that bundles everything an application needs to run — code, runtime, system tools, libraries, and settings. Unlike a virtual machine, which virtualizes an entire operating system, a container shares the host machine's OS kernel. That's what makes it so much more efficient: a typical container starts in milliseconds and uses megabytes of memory, while a VM can take minutes to boot and needs gigabytes of RAM.

Images and containers aren't the same thing. An image is a read-only template — a blueprint — and a container is a running instance of that image. Images are built in layers, with each instruction in a Dockerfile adding a new one. That layered structure is why rebuilds are fast: Docker reuses any layer that hasn't changed instead of rebuilding it from scratch.

Isolation is the other piece. Every container runs in its own namespace, so its processes, network interfaces, and file system stay separate from the host and from other containers. That's also what solves the old "it works on my machine" problem — the same image behaves identically on a laptop, a staging server, and production, because it's carrying its environment with it.

Between the efficiency and the consistency, it's easy to see why Docker changed how teams build, ship, and deploy software: less overhead, fewer environment surprises, a more reliable path from code to production.

## Task 8 — 08-explainer-oauth.md

# OAuth 2.0 Explained for Junior Developers

Every time you click "Sign in with Google," you're watching OAuth 2.0 work — it's the industry-standard protocol for letting one application access your data on another service without ever seeing your password.

The first thing to get straight: OAuth handles authorization, not authentication. Authentication is about who you are; authorization is about what you're allowed to access. When a third-party app uses OAuth to reach your email or calendar, it's requesting permission to act on your behalf — your password never enters the picture.

Four parties are involved: the resource owner (you), the client (the app requesting access), the authorization server (which issues tokens), and the resource server (which holds the actual data).

The flow you'll run into most often is the Authorization Code flow. The client sends you to the authorization server, where you grant consent. The server hands back an authorization code to the client's redirect URI. The client then trades that code — along with its client secret — for an access token, and uses that token to pull data from the resource server.

Access tokens don't last long, usually about an hour, so refresh tokens exist to get a new one without making you log in again. Single-page apps get an extra layer here: the PKCE extension removes the need to store a client secret in the browser at all, which would otherwise be a security hole.

Get these pieces down and the rest of OAuth — and most of the API security you'll run into — stops feeling like a black box.

## Task 10 — 10-linkedin-failed-launch.md

Six months ago we shipped a product nobody wanted.

We launched Cartwheel after 14 months of building what we thought was a game-changing tool for freelance invoicing. The design was good, the feature set was solid, onboarding was smooth. What we didn't have was customers — 87 users in the first month, and a trial-to-paid conversion rate of 1.2%. The numbers said it plainly: we'd built something people didn't need.

A few things that failure taught me. Validation has to be a habit, not a box you check once — we talked to 15 potential users before building, and it should've been closer to 100. Loving the problem instead of the solution isn't just something people say; it's what keeps you honest, and we skipped it — we fell for our own product and it blinded us. And speed beats polish: we spent 14 months refining features nobody had asked for, while a competitor shipped in 4 months and iterated their way to product-market fit.

Failing isn't the problem. Failing slowly, after you've burned all your runway, is.

We've pivoted since, and it's working — 2,300 users now, growing 15% a month. To anyone else sitting with a setback right now: it's not your identity. It's your education.
