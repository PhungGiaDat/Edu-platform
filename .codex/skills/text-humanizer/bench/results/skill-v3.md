## Task 2 — 02-blog-coffee-brewing.md

Coffee is more than just a beverage — it's part ritual, part science. Home brewing enthusiasts are increasingly discovering that crafting a great cup doesn't require a trip to an expensive café. With the right knowledge and a few key tools, anyone can turn their morning routine into something special.

At its core, great coffee comes down to four key variables: grind size, water temperature, brew time, and ratio. A ratio of 1:16 — one gram of coffee to sixteen grams of water — is a solid starting point for most brewing methods. Water temperature matters too: the ideal range sits between 90 and 96 degrees Celsius, since water that's too hot extracts bitter compounds while water that's too cool leaves the cup tasting sour and underdeveloped.

Freshness matters a lot, too. Coffee beans start losing their aroma within two weeks of roasting, so buy whole beans in small batches and grind them just before brewing.

From pour-over to French press, from AeroPress to cold brew, each method offers its own range of flavors to explore. In this guide, we'll cover the fundamentals that will make your daily cup better.

## Task 7 — 07-explainer-docker.md

# Understanding Docker Containers

Docker has become one of the most important technologies in modern software development, fundamentally changing how applications are built, shipped, and deployed. But what exactly is a container, and why does it matter so much to engineering teams?

At its core, a Docker container is a lightweight, standalone, executable package that includes everything an application needs to run: code, runtime, system tools, libraries, and settings. Unlike virtual machines, which virtualize an entire operating system, containers share the host machine's OS kernel, making them significantly more efficient. A typical container starts in milliseconds and consumes megabytes of memory, whereas a virtual machine can take minutes to boot and requires gigabytes of RAM.

Images and containers are different things. A Docker image is a read-only template — a blueprint — while a container is a running instance of that image. Images are built in layers, and each instruction in a Dockerfile creates a new layer. This layered architecture enables efficient caching: when you rebuild an image, Docker reuses unchanged layers, dramatically speeding up the build process.

Containers also provide strong isolation. Each container runs in its own namespace, so processes, network interfaces, and file systems stay separate from both the host and other containers. This is one of Docker's key benefits: consistency across environments. The famous "it works on my machine" problem becomes a relic of the past, since the same image runs identically on a developer's laptop, a staging server, and production infrastructure.

Docker containers offer an efficient, portable approach to application deployment. By embracing containerization, teams can simplify their workflows, cut infrastructure costs, and build a more reliable development lifecycle.

## Task 8 — 08-explainer-oauth.md

# OAuth 2.0 Explained for Junior Developers

Authentication and authorization are two pillars of modern web security, and OAuth 2.0 is the industry-standard protocol for delegated authorization. If you've ever clicked "Sign in with Google," you've experienced OAuth in action. Here's how it actually works.

OAuth is about authorization, not authentication. Authorization determines what you can access, while authentication verifies who you are. OAuth 2.0 allows a third-party application to access a user's resources — such as their email address or calendar — without ever seeing the user's password.

The protocol involves four key roles: the resource owner (the user), the client (the application requesting access), the authorization server (which issues tokens), and the resource server (which hosts the protected data). These roles work together to keep the process secure at every step.

The most common flow is the Authorization Code flow. It works as follows: the client redirects the user to the authorization server, where the user grants consent. The authorization server then returns an authorization code to the client's redirect URI. The client exchanges this code — along with its client secret — for an access token. Finally, the client uses the access token to request resources from the resource server.

Access tokens are typically short-lived, often expiring after one hour, and refresh tokens allow clients to obtain new access tokens without prompting the user again. For single-page applications, the PKCE extension (Proof Key for Code Exchange) adds an additional layer of protection by eliminating the need to store a client secret in the browser.

Understanding these foundational concepts will set you up to handle modern API security.
