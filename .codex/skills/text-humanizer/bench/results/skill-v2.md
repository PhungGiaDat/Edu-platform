## Task 2 — blog intro, coffee brewing
Source: `bench/materials/02-blog-coffee-brewing.md`

Coffee is a ritual, a science, and an art form all rolled into one. Home-brewing enthusiasts are increasingly discovering that crafting the perfect cup doesn't require a trip to an expensive café. With the right knowledge and a few key tools, anyone can turn their morning routine into something truly special.

At its core, great coffee comes down to four variables that matter: grind size, water temperature, brew time, and ratio. A ratio of 1:16 — one gram of coffee to sixteen grams of water — is a solid starting point for most brewing methods. Water temperature matters just as much; the ideal range sits between 90 and 96 degrees Celsius, since water that's too hot extracts bitter compounds while water that's too cool leaves the cup tasting sour and underdeveloped.

Freshness matters too. Coffee beans start losing their aroma within two weeks of roasting, so it's worth buying whole beans in small batches and grinding them right before brewing.

From pour-over to French press, from AeroPress to cold brew, each method brings out different flavors. This guide covers the fundamentals to get more out of your daily cup.

## Task 7 — technical explainer, Docker
Source: `bench/materials/07-explainer-docker.md`

# Understanding Docker Containers

Docker has fundamentally changed how applications are built, shipped, and deployed. But what exactly is a container, and why has it become so important to modern engineering teams?

At its core, a Docker container is a lightweight, standalone, executable package that includes everything an application needs to run: code, runtime, system tools, libraries, and settings. Unlike virtual machines, which virtualize an entire operating system, containers share the host machine's OS kernel, making them significantly more efficient. A typical container starts in milliseconds and consumes megabytes of memory, whereas a virtual machine can take minutes to boot and requires gigabytes of RAM.

Images and containers aren't the same thing. A Docker image is a read-only template — a blueprint — while a container is a running instance of that image. Images are built in layers, and each instruction in a Dockerfile creates a new layer. This layered architecture enables efficient caching: when you rebuild an image, Docker reuses unchanged layers, dramatically speeding up the build process.

Containers also provide strong isolation. Each container runs in its own namespace, ensuring that processes, network interfaces, and file systems remain separate from both the host and other containers. This isolation is behind one of Docker's key benefits: consistency across environments. The famous "it works on my machine" problem becomes a relic of the past, as the same image runs identically on a developer's laptop, a staging server, and production infrastructure.

By adopting containers, teams can streamline their workflows, reduce infrastructure costs, and build a more reliable development lifecycle.

## Task 8 — technical explainer, OAuth
Source: `bench/materials/08-explainer-oauth.md`

# OAuth 2.0 Explained for Junior Developers

Authentication and authorization are core pieces of modern web security, and OAuth 2.0 is the industry-standard protocol for delegated authorization. If you've ever clicked "Sign in with Google," you've experienced OAuth in action. Here's how it actually works.

First, OAuth is about authorization, not authentication. Authorization determines what you can access, while authentication verifies who you are. OAuth 2.0 allows a third-party application to access a user's resources — such as their email address or calendar — without ever seeing the user's password.

The protocol involves four key roles: the resource owner (the user), the client (the application requesting access), the authorization server (which issues tokens), and the resource server (which hosts the protected data). These roles work together to keep the process secure at every step.

The most common flow is the Authorization Code flow. It works as follows: the client redirects the user to the authorization server, where the user grants consent. The authorization server then returns an authorization code to the client's redirect URI. The client exchanges this code — along with its client secret — for an access token. Finally, the client uses the access token to request resources from the resource server.

Access tokens are typically short-lived, often expiring after one hour, and refresh tokens allow clients to obtain new access tokens without prompting the user again. For single-page applications, the PKCE extension (Proof Key for Code Exchange) adds an additional layer of protection by eliminating the need to store a client secret in the browser.

Once these concepts click, the rest of modern API security gets a lot easier to reason about.

Today, I want to share the lessons that failure taught me.

When we launched Cartwheel, our team was confident. We had spent 14 months building what we believed was a breakthrough solution for freelance invoicing. We had beautiful designs, solid features, and a smooth onboarding flow. What we didn't have was customers.
